# Тестовое задание: бэкенд-ядро магазина цифровых товаров

Полный текст: [test_task_kudrya.pdf](test_task_kudrya.pdf).

Ниша вроде GGSel: платежи (заглушка), поставщики (две заглушки), каталог, авто-выдача кода. Оплату эмулирует тот же скрипт, что проверяет гонки. Реального эквайринга нет.

## Стек

PHP 8.3, Laravel 11, PostgreSQL 16, REST, очередь (sync/redis), вебхуки.

## Этапы

1. Ядро API: заказ по SKU, GET заказа, вебхук оплаты, авто-выдача, статусы.
2. Exactly-once под гонками: дубли и параллельные вебхуки → один код. Скрипт `scripts/race_webhook.php` (50 параллельных).
3. Два поставщика, таймауты, backoff, fallback A→B. Таймаут ≠ отказ: тот же `request_id`.
4. Логи, сверка «оплачен не выдан» / «выдан не оплачен», фоновое дожимание, ledger.
5. Тысячи SKU, горячая витрина, индекс, `catalog:explain`.

## Критерии приёмки

1. 50 параллельных вебхуков paid → одна выдача.
2. Повтор того же `event_id` ничего не меняет.
3. Вебхук раньше заказа → 503 (ретрай); `failed` затем `paid` обрабатываются; поздний `failed` не откатывает выдачу.
4. Таймаут поставщика, который выдал код → повтор не создаёт второй код.
5. A недоступен → fallback B, товар один раз.
6. Пустой пул ключей → `out_of_stock`, без падения; после пополнения сверка/повтор доводит до `delivered`.

## Контракт вебхука

`POST /api/webhooks/payment`: `event_id`, `order_id`, `status` (`paid`|`failed`), `amount` (RUB), `currency`, `created_at`. At-least-once, может прийти не по порядку. 200 принято; 5xx — повтор доставки. Подпись не проверяется.

## Поставщик

Семантика `POST /issue`: `{ request_id, sku, order_id }`. Успех: `{ status: ok, request_id, code }`. Ошибка: `{ status: error, reason: out_of_stock }`. Повтор с тем же `request_id` — тот же код. Пул ключей из приложения ТЗ, один ключ — один заказ.

## Статусы

`created` → `paid` → `delivering` → `delivered`  
`created` → `payment_failed`  
`delivering` → `out_of_stock` | `delivery_failed` (восстановимые) → снова `delivering` → `delivered`.
